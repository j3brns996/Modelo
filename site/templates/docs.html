01 / Choose a mode

Choose an intake path

Browse

A colleague looks for a model and its Offering. Read the route, rationale and Conditions. A model name or provider listing alone is not permission.

Discover and draft

A steward asks an agent to collect read-only observations and prepare a proposal. The browser helper, CLI and agent skill are authoring aids, not approval authorities.

Operational change: MAC

Change Model, Offering or Evidence records under the accepted rules. Start with a linked MAC issue, then submit the record changes for exact-head checks and independent review.

System change

Change code, schemas, validation, workflow rules or this site in a separate engineering PR. Schemas are rules, even when written as JSON. Human CODEOWNER review is required.

No mixed proposals. If an operational change needs new rules, accept the system change first, then submit the MAC. Synthetic fixtures under test paths belong with system changes; they are not operational approvals. Changing a versioned Condition requires authorised policy review.

02 / People and responsibilities

Roles and decisions

Requester or steward
Explains the need, supplies scope and prepares the proposal.
Discovery agent
Collects evidence and drafts records. It cannot approve, merge or bypass policy.
Independent reviewer
Checks the evidence and proposed decision at the exact commit. Agent approval is currently disabled.
Maintainer / CODEOWNER
Reviews system changes and controls protected-branch acceptance.
AI-use owner
Records the application, purpose, data and human oversight in the separate organisational inventory.

03 / The NIST inventory context

Component registry scope

  • Supports selected NIST AI RMF outcomes
  • Not a certification
  • Not a complete organisational AI-system inventory

For example: Nova 2 Lite identifies a named release. Nova 2 Lite through Bedrock in eu-west-2 describes a possible Offering. Customer-call summarisation in Adviser Desktop is an AI use, recorded elsewhere. These are illustrations, not production catalogue entries.

Covered-by-parent is not exemption. An embedded meeting-summary feature may be represented within its parent application when all of the organisation's coverage criteria hold. Material changes trigger reassessment. If any coverage criterion fails, a separate external AI-use entry is required: for example, a distinct purpose, owner or data-risk profile, a separately managed route, or consequential/autonomous use. An undisclosed underlying model stays “not disclosed”; do not invent a mapping.

Current support: GOVERN 1.6 and GV-1.6-001 are partial; GV-1.6-002 is supporting evidence only; GV-1.6-003 is partial within the component boundary. The bounded model/version/access-mode contribution to 003 targets design equivalence. These are assessable method comparisons, not compliance scores.

Maturity: M1, a governed component registry, is the project target. Linked uses, reconciliation and continuous assurance depend on external systems and operating evidence. Production publication and T10 remain outstanding. Synthetic tests cannot prove operating equivalence.

Official sources: NIST AI RMF Core and NIST Generative AI Profile. The repository's assurance mapping records scope, limitations, ownership and assessment criteria.
