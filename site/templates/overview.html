How Modelo works

Modelo records model identities, approved access routes, and the evidence for each decision.

What does Modelo record?

A model record identifies a named release. An offering records a permitted way to access that release. Evidence supports external facts. Versioned conditions record enterprise constraints. A model record alone does not grant permission to use it.

Primary keys and foreign keys in practice

PK and FK are shorthand here. Git does not enforce primary keys, foreign keys, joins, or cascading deletes. Modelo checks identities and references across a candidate snapshot. Trusted CI must pass for the exact proposed commit.

Keys stored in the catalogue
Key or referenceMeaning
model.id, offering.idStable internal keys. Paths locate files; moving a file does not redefine identity.
model.vendor_idReferences a key in the vendor registry.
offering.model_id, inference_service_idReference the model and service. A change to the model binding requires a new offering.
route.idUnique within its offering, not a global model key.

evidence_refsMap a record fact pointer to an evidence ID and evidence pointer. Validation checks the referenced value.

A provider model reference is noncanonical. A route's reference belongs to the provider. It may select a model or a routing profile. It is not Modelo's model key and does not prove immutable weights. Evidence must establish its binding to the internal model record. The optional link or name in a request is also unverified input.

Modelo's canonical identity is internal: model.id and its derived urn:modelo:model-release:<id>. It is not a universal identifier shared by all providers. Git commit IDs identify revisions; they are not entity keys. Family IDs group records and are not a separate entity registry.

Why use Git?

Catalogue decisions change less often than provider inventory. Git provides revision history and diffs. The Git provider adds issues, review, protected branches, and CI. Using these existing controls keeps the approval record close to the data it governs.

A reviewer can compare a proposed change, inspect its evidence, and identify the exact commit checked by CI. Clones and release artifacts support portable records. Git history is tamper-evident, not write-once storage; host permissions, backups, and remote control tests still matter.

Git fits a reviewed catalogue. It does not supply live entitlement checks, runtime enforcement, transactional queries, or row-level access control. Review capacity and measured operating needs determine when another store is justified.

Who does what?

  • The requester describes the need and can supply a model or provider link.
  • A maintainer or agent prepares records and gathers evidence.
  • Trusted CI checks the exact candidate against the repository rules.
  • An independent reviewer assesses the decision. Human CODEOWNER review is required for code, schemas, policy, and workflow changes.
  • The application owner manages purpose, data, oversight, and use risks in the external inventory.

Agent approval is disabled. Agents do not merge or bypass controls.

Where are the files and models?

Git holds catalogue records, retained evidence envelopes, conditions, and source code. The site publishes a validated projection. Modelo does not store or serve .pkl files, model weights, checkpoints, or inference runtimes. Those artifacts remain with the supplier or in a separately governed artifact store. A model-card link is documentation, not a copy of the model.

GitHub and GitLab provide intake and review. Their URLs are configured in modelo.yaml. Application inventories and runtime systems remain separate.

Embedded AI in vertical products

AI embedded in products such as clinical software or a sales platform is outside Modelo's current component catalogue scope. The external application or AI-use inventory owns that use and its review. Record an undisclosed model as unknown; do not invent a model or offering binding.

This is a Modelo scope boundary, not a NIST exemption. NIST AI RMF addresses third-party risks in GOVERN 6 and MAP 4. A parent application entry can cover a feature under the organization's coverage criteria; ownership, supplier review, and change review still apply. NIST AI RMF Core.

External inventory links, coverage criteria, and reconciliation are in backlog issue 78. They are not implemented approval controls.

When is review required?

Review every proposed catalogue change before acceptance. New evidence, changed route binding, changed processing location, or changed conditions can affect the decision. Refresh evidence by creating a new immutable record and reviewing its references. Missing discovery results do not automatically revoke an offering.

A new commit invalidates prior checks and approval. A changed purpose, data context, level of autonomy, supplier, or control also calls for review by the external AI-use owner. An existing offering does not approve every application.

When should the architecture change?

The specification calls for an architecture review after 90 days. Reconsider the operational store when any two of these conditions persist for four weeks:

  • More than 50 accepted changes per working day.
  • Repeated peaks above 10 changes per hour with a publication target under one hour.
  • More than 10% of catalogue changes need conflict resolution.
  • The 95th percentile of issue-to-publication time exceeds one business day while review utilization stays below 70%.
  • The 95th percentile of validation exceeds five minutes or publication exceeds ten minutes.
  • More than 5% of changes bypass the workflow.
  • The same identity normally changes more than once a day.
  • Consumers need transactions, row-level access, or live state.
  • A supported baseline clone takes more than 60 seconds because of retained data.

These are review criteria, not measured results. Retain accepted release snapshots in Git if operational state moves elsewhere.
